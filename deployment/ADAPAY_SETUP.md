# AdaPay 接入与部署

本版本为云速取增加 AdaPay 原生微信小程序支付、个人实名与银行卡结算账户、90:10 延时分账，以及未分账订单取消后的原路退回。线上支付费率按商户后台的 **0.66%** 执行；代码不重复加收该费用。银行卡到账遵循支付机构账户的实际结算配置，不增加八小时自动提现任务，也不自动更改后台产品。

## 云函数环境变量

在 `mcloud → 版本与配置 → 配置 → 环境变量` 填写，禁止提交凭据到 Git。

| 变量 | 值或来源 |
| --- | --- |
| `PAYMENT_PROVIDER` | `adapay`，只影响新订单；原有微信订单仍走原渠道 |
| `ADAPAY_APP_ID` | AdaPay 应用号，通常为 `app_...`，不是微信 AppID |
| `ADAPAY_PROD_MODE` | `false` 使用模拟环境；真实联调使用 `true` |
| `ADAPAY_API_KEY` | 与模式对应的 `api_test_...` 或 `api_live_...` |
| `ADAPAY_PRIVATE_KEY` | 与后台商户 RSA 公钥配套的 PKCS8 私钥 |
| `ADAPAY_PUBLIC_KEY` | AdaPay RSA 公钥，不是商户公钥 |
| `ADAPAY_IDENTITY_HMAC_KEY` | 单独随机生成的至少32字节服务端密钥，保持稳定并安全备份 |
| `ADAPAY_NOTIFY_URL` | 云函数 HTTP 接入地址，HTTPS，路径以 `/adapay/notify` 结尾，无查询参数 |
| `WECHAT_APP_ID` | 已关联 AdaPay 渠道的云速取微信 AppID |

PEM 支持完整多行、字面 `\n`，也支持后台导出的无头尾 Base64。不要把私钥当成 API Key。不要使用旧微信支付私钥填充 AdaPay 配置。

缺少或格式不正确的必要配置时，新订单阻止在线发布，不自动回退为线下订单。模拟、正式模式的开户记录相互隔离。

## 部署顺序

1. 本地完成测试，先部署代码，再按计划启用 `PAYMENT_PROVIDER=adapay`，避免旧代码读取新配置。
2. 在微信开发者工具右键 `cloudfunctions/mcloud`，选择“上传并部署：云端安装依赖”。此接入使用 Node 内置密码与 HTTPS 模块，未新增第三方依赖。
3. 将 HTTP 网关的 `/adapay/notify` POST 路由关联到 `mcloud`，原样传递 body、headers、httpMethod、isBase64Encoded，不做 JSON 重写、登录重定向或签名内容改写。旧微信回调路由保留。
4. 上传并检查原有 `orders-minute` 定时触发器；回调验签后只排入核对队列，资金终态由签名查询结果确认，因此定时任务必须运行。
5. 重新编译并上传小程序；先在隔离测试环境验证模拟模式，再做经过授权的小额真实联调。模拟支付不能证明真实开户、出款或银行到账。

## 资金与数据边界

- 延时模式创建支付时不传 `fee_mode`（实测传入非空值会返回 `fee_mode_not_blank`），也不传分账列表；在订单完成、创建支付确认/分账时使用 `fee_mode=O`，请求从商户手续费账户扣费。需在服务商后台确保外扣可用、账户余额充足，并在真实账单中核实费用承担方。外扣不支持或余额不足时停留待处理，不改为从骑手报酬扣费。
- 后端以存储的订单金额为准，按分计账；跑腿收益向下取整到分，余数归平台。完成确认后由支付机构在原支付中分账，平台不先提取全部资金再转账给跑腿。
- 未付款取消关闭支付；付款后未分账取消走支付撤销。创建撤销成功只表示受理，查询终态成功后才标记已退款。已分账订单不提供自助退款，争议联系平台人工处理。
- 原微信订单的密钥和回调保留，直到原订单的退款、报酬结算全部结束。
- 开户信息经过云函数短暂转交，不宣称前端直传。完整姓名、身份证号、银行卡号、预留手机号不写缓存、数据库或日志。仅存账户标识、状态、脱敏姓名、卡尾号、授权版本与时间、HMAC摘要。
- 开户账户按当前校区隔离；仅雁山校区开放服务。后续拓展校区时需设计账户复用迁移。
- 绑卡请求超时、成功应答丢失时，禁止再次盲目创建结算账户。使用相同资料重试时，服务端只读查询原 member_id 的 settle_accounts，验证应用、正式/模拟环境、实名状态、账户类型及银行卡可见号码；只有唯一匹配的成功账户才自动恢复。本地仅保存账户标识和既有脱敏信息，不保存查询原文。接口未返回足够资料、查不到或有多个匹配账户时继续待核对，由管理员与 AdaPay 核实，不要仅修改状态为 ready。
- 不自动设置渠道最低提现额、单笔或每日限额，不绕过机构限制。本期沿用机构自动结算，没有新增主动提现入口。

## 上线验收

验证付款后才公开订单、无开户不能接单、本人实名绑卡、重复点击和通知不重复分账、取消退款、取消与付款交错、90:10分账、平台承担费用、银行卡真实到账。分账成功页面显示“已分账”，不显示“银行已到账”。开户信息不能出现在云日志中。

官方依据：[Node SDK](https://docs.adapay.tech/sdk/nodesdkaccess.html)、[交易及开户](https://docs.adapay.tech/api/trade.html)、[异步通知](https://docs.adapay.tech/api/webhook.html)。HTTP 签名与通用实名路径已对照官方 Node SDK 1.3.1 的 Http.js 和 Java SDK 1.2.10 的 AdapayCommon.java 核实；未引入 SDK 的原始报文日志实现。


## 定时入口排查

`Route Not Defined` 表示请求进入普通接口且缺少 route，不能据此判定 AdaPay 请求失败，也不能仅凭分钟级时间戳判定是定时调用。入口兼容 `Type: Timer`、`Type: timer` 及 `type: timer / triggerName`，并继续使用可信 WXContext 拒绝有 OPENID 的调用。

重新上传 mcloud 代码后，定时入口会打印 `YUNSUQU_ENTRY_TIMER_V2`，任务完成打印 `YUNSUQU_TIMER_DONE`。无 route 且未识别为定时事件时打印 `YUNSUQU_ENTRY_UNROUTED_V2`，仅包含输入类型及约定字段是否存在，不输出完整事件。如果同一次新调用仍只有旧的 `Route Not Defined` 而没有 V2 标记，需要核对所上传的本地项目目录、云环境、执行入口 index.main 及触发器使用的版本，避免重复部署旧副本。


2026-11-25 实际响应兼容：GET 请求与官方 SDK 一致，不发送 JSON Content-Type；错误添加该请求头会导致查询返回 app_not_exists。用户查询中的 settle_accounts 是摘要，不能要求它包含 status/prod_mode，必须带 member_id、settle_account_id 再查询完整结算账户。银行卡掩码可能保留前10位和后1位，不能固定比较后4位；需校验所有可见号码且至少8位可见数字，匹配不唯一或详情校验不通过时不恢复开通。不修改既有商户配置，也不重复创建已提交的绑卡请求。


## 分账成功后的状态同步

2026-11-25 的真实支付确认详情已验证不含 payment_id。核对成功依靠已验签的对象ID、应用、环境、唯一请求单号、金额与分账接收方；若返回 payment_id，仍检查其与原支付一致。分账创建受理后保存 operationId，列表尚未收录时直接查询该对象，不再次提交。若列表对象与已保存ID冲突，停留待核对，不标记成功。

部署 mcloud 后，原先停留 paid/pending 的记录可由 orders-minute 定时任务重新查询并同步为 complete/settled。随后刷新订单，页面应显示“报酬已分账”；不要通过后台直接改状态或手工重新分账。

分账成功仅表示资金已分配到支付机构账户，不代表银行卡到账。需在 AdaPay 的结算查询中核对结算明细、状态和机构实际结算周期。2026-11-26 的只读核对显示两笔测试分账成功、fee_mode=O；对应日期范围尚未返回银行卡结算明细，此结果不等于已到账，也不说明未来具体到账时间。


新用户重试开户：本地已有失败申请、AdaPay 尚未创建用户时，查询会返回 member_not_exists。该错误只在响应已验签且明确表示用户不存在时允许继续创建原 member_id，兼容旧版 member_not_exist/user_not_exist/user_not_exists。配置错误、网络失败或未验签响应继续待核对，不据此重新开户。无需删除本地失败记录或更换应用密钥。
